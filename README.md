# Calorie Counter

The optional [AI assistant MCP integration](docs/chatgpt-mcp.md) (ChatGPT, Claude) supports natural-language
meal logging and cooking through scoped, authenticated tools.

A multi-person calorie tracking app built with TanStack Start, Convex, and
Clerk authentication.

## Stack

- TanStack Start (React 19 + file-based TanStack Router)
- Vite + TypeScript
- Tailwind CSS v4
- shadcn/ui + `@base-ui/react` primitives
- Convex (backend, schema, queries, mutations)
- Clerk (required authentication and Convex identity)

## App Routes

- `/`: Today: focused intake for the person remembered on this device, date-aware goals, recorded meal details, and optional meal entry/correction. Reveal household intake to check or select someone else.
- `/history`: Person-scoped history with complete-range loading and links back to a day's meals.
- `/settings/archived-meals`: Inspect and restore archived meals by person and day.
- `/settings`: People, household, AI assistants, and data-maintenance links.
- `/people`: Browse-first people and goal settings, with goal history inside each person.
- `/catalog`: Food library for MCP reusable foods, ingredients, recipes, and optional groups.
- `/cooking`: Cooked-batch inspection, composition/weight correction, and old-draft recovery. Record new cooking through an AI assistant.
- `/household`: Household naming, invitations, roles, and membership.
- `/settings/integrations`: Connected assistants and account-level logging defaults.
- `/connect`: OAuth connection consent.

Primary navigation is Today, History, and Settings. Existing route, household,
person/date, session, and invitation links remain supported. Inspecting daily
intake does not load ingredient or cooking pickers; editors load when opened.
History uses dated goals and excludes days without meals from its explicitly
labeled average, while including logged zero-calorie meals.

## Convex Domain Model

The Convex schema currently includes:

- `households`, `householdMembers`, `householdInvitations`

- `people`, `personGoalHistory`
- `foodGroups`, `ingredients`
- `recipes`, `recipeVersions`, `recipeVersionIngredients`
- `cookSessions`, `cookedFoods`, `cookedFoodIngredients`
- `meals`, `mealItems`
- `dailySummaries`
- `mcpPreferences`, `mcpSavedFoods`, `mcpOperations`

Backend functions live under `convex/`. Files in `convex/_generated/` are
generated by Convex and must not be edited by hand.

## Architecture

TanStack Start is intentionally retained while authenticated feature routes
render on the client and subscribe directly to Convex. The rationale and
conditions for revisiting that choice are recorded in
[`docs/adr/0001-client-only-tanstack-start.md`](docs/adr/0001-client-only-tanstack-start.md).

## Households

Accounts can belong to multiple households. Every household member can view and
manage its people, goals, catalog, recipes, cooking, meals, and history. Admins
manage the household name, invitations, and other members. The last admin must
promote another member before leaving or stepping down. Removing an account
never deletes tracked people or historical nutrition data.

Open **Settings → Household** to switch households or create a
single-use invitation link, valid for seven days. Anyone with the link can accept
it, so share it privately. The recipient reviews what sharing includes before joining. Invitations can be revoked.
Joining adds access; existing households and their data stay separate. An
account that leaves its last household can accept a new invitation from the
recovery screen; signing in again never restores removed access automatically.
Invitation management has pagination so older active links remain reachable for
revocation even after newer links have been used or revoked.

The selected household and person persist in local storage per account and
household on each device. Meal drafts and focused cooking edits remain per tab,
account, and household. The retired cooking workspace's local drafts can be
recovered, exported, or explicitly discarded; an old edit without a safe revision
baseline must be exported and applied to a freshly opened record. Switching
households remounts feature state. A saved
person that is archived or unavailable must be replaced explicitly.

On first use, the app creates an account's personal household. Every domain
record has a required `householdId`, and all authorization, indexes, and
searches use it. `ownerTokenIdentifier` records which account wrote a row; it
does not grant access.

## Local Setup

1. Use the Node version declared in `package.json`, then install locked dependencies.

```bash
pnpm run setup:worktree
```

`pnpm-workspace.yaml` disables Node's experimental Web Storage for pnpm-launched
scripts and commands, preserving caller-supplied `NODE_OPTIONS`. This prevents
Vitest's edge-runtime global copying from invoking Node's `localStorage` getter
without a storage file. Browser and jsdom storage are unaffected, and other Node
warnings remain enabled. Direct `node` invocations bypass this pnpm setting.

For browser tests and visual iteration without account credentials, see
[the synthetic browser workflow](e2e/README.md). Normal development below uses
your selected Clerk and Convex development environment.

2. Create `.env.local`.

```bash
VITE_CONVEX_URL=
CONVEX_DEPLOYMENT=
VITE_CLERK_PUBLISHABLE_KEY=
```

All three variables are required for normal local development:

- `VITE_CONVEX_URL` connects the browser to Convex.
- `CONVEX_DEPLOYMENT` selects the deployment used by Convex tooling.
- `VITE_CLERK_PUBLISHABLE_KEY` initializes Clerk. Authenticated application
  routes are unavailable without it.

3. Create a Clerk JWT template for Convex.

In Clerk Dashboard:

- Go to `JWT Templates`
- Create template named `convex`
- Set audience to `convex`

`convex/react-clerk` requests `getToken({ template: "convex" })`, so this template must exist.

4. Configure Convex auth provider env for Clerk.

```bash
pnpm exec convex env set CLERK_JWT_ISSUER_DOMAIN https://<your-clerk-domain>
```

This value is used by `convex/auth.config.ts` and is required for signed-in users to access Convex queries/mutations.

5. Start Convex in a separate terminal.

```bash
pnpm exec convex dev
```

6. Start the app.

```bash
pnpm run dev
```

App runs at [http://localhost:3000](http://localhost:3000).

## Seed Data

Vercel runs this as the build command (`buildCommand` in `vercel.json`), so
each pull request preview it builds gets a seeded Convex preview deployment.
Renovate previews are skipped:

```bash
pnpm exec convex deploy --cmd 'pnpm run build' --preview-run seed:defaults
```

The seed function creates default people, catalog items, a recipe, a cook
session, cooked food, and a sample meal. Its date defaults to the current UTC
calendar date; pass `eatenOn` in `YYYY-MM-DD` format or set `SEED_EATEN_ON` on
the Convex deployment when the sample should appear on a different local date.
It is idempotent for the target owner and date. Seeding requires an
issuer-qualified `SEED_OWNER_TOKEN_IDENTIFIER` in
`issuer|subject` form unless the call is authenticated. `SEED_OWNER_USER_ID` is
an optional helper for deriving and validating that identifier; it is not
stored in application records. Preview deployments may derive the identifier
from `CLERK_JWT_ISSUER_DOMAIN` plus `SEED_OWNER_USER_ID`. For an existing
selected deployment, set:

```bash
pnpm exec convex env set SEED_OWNER_TOKEN_IDENTIFIER 'https://issuer.example|user_...'
pnpm exec convex env set SEED_OWNER_USER_ID user_...
```

For a selected dev deployment, you can also pass the owner directly:

```bash
pnpm run seed:defaults -- '{"ownerTokenIdentifier":"https://issuer.example|user_...","ownerUserId":"user_...","eatenOn":"2026-04-04"}'
```

For local runs, `pnpm run seed:defaults` forwards `SEED_OWNER_USER_ID` and
`SEED_OWNER_TOKEN_IDENTIFIER` from your shell or `.env.local` as Convex function
arguments. For `--preview-run`, those values must be configured as Convex
deployment env vars because the function runs on Convex, not in the Vercel build
shell. `ownerUserId` alone is not sufficient.

## Maintenance Mode

Build and deploy the frontend with `VITE_MAINTENANCE_MODE=true` to show a
maintenance page before Clerk, Convex, or application queries initialize. It is
only a user-facing notice. To stop backend writes, use Convex's
[Pause deployment](https://docs.convex.dev/production/pause-deployment)
control. Rehearse any destructive production operation on a disposable
deployment first.

## Scripts

- `pnpm run setup:worktree`: Install dependencies without changing the lockfile
- `pnpm run dev`: Start local dev server (port `3000`)
- `pnpm run dev:e2e`: Review real components with synthetic data (loopback port `4173`)
- `pnpm run build`: Production build (client + SSR bundles)
- `pnpm run preview`: Preview production build
- `pnpm run seed:defaults`: Seed the selected Convex deployment with default data
- `pnpm run format`: Format first-party files with Prettier
- `pnpm run format:check`: Verify formatting without changing files
- `pnpm run lint`: Run ESLint
- `pnpm run lint:fix`: Run ESLint with autofix
- `pnpm run typecheck`: Type-check the app and Convex backend
- `pnpm run test`: Run the Vitest unit, route, and Convex test suites
- `pnpm run test:coverage`: Run the test suite and write a coverage report
- `pnpm run test:e2e`: Run the mocked authenticated dashboard smoke test in Chromium

## Dependency Security

This project commits `pnpm-workspace.yaml` to keep installs predictable:

- Peer dependencies are not installed implicitly.
- New package resolutions must be at least 3 days old.
- Only explicitly allowed dependency build scripts may run.
- The `esbuild` override remains pinned for reproducible builds.

Use checked-in tooling through `pnpm exec` instead of ad-hoc downloads. These defaults reduce package-manager risk, but they do not sandbox build or dev-server code. For dependency updates, prefer targeted updates inside a container or dedicated OS user without personal secrets mounted:

```bash
pnpm outdated
pnpm update <package>
pnpm run lint
pnpm run typecheck
pnpm run build
```
